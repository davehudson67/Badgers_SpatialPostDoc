# Woodchester Badger Database — simple R guide

This is the short guide to the new Woodchester badger database in **Supabase/PostgreSQL**.

For most users there are only three things to remember:

1. connect using `scripts/BadgerDatabase.R`;
2. start with the ready-made views in the `analysis` schema;
3. only use the lower-level `research` tables when you need something more specific.

The original Microsoft Access data are preserved separately and should normally be left alone.

---

## 1. How the database is organised

There are three main schemas.

| Schema | What it is | When to use it |
|---|---|---|
| `access_raw` | Preserved import of the original Access database | Auditing old records or resolving cleaning questions only |
| `research` | Cleaned relational tables | When you need detailed capture, sample, test or location fields |
| `analysis` | Ready-to-use analysis views | **Start here for most analyses** |

A useful mental model is:

```text
Original Access database
        ↓
access_raw
        ↓
cleaned relational tables
        ↓
research
        ↓
ready-to-use analysis views
        ↓
analysis
        ↓
R analysis / model-input snapshots
```

The live PostgreSQL database is the canonical data source. Major modelling scripts should normally use frozen RDS snapshots produced from it rather than repeatedly querying the live database.

## 2. The main ready-to-use analysis views

### `analysis.capture_history`

**One row per capture.**

This is the main table for most capture-history work.

It contains the cleaned identifiers and core fields needed for things such as:

- badger ID and tattoo;
- capture date;
- year and quarter;
- sex and age;
- live versus post-mortem record;
- cleaned sett information;
- the social group recorded on that capture;
- other capture-level fields used by the project.

Use this first for CMR, SCR, movement and basic demographic analyses.

**Important:** the capture-recorded `socg` is the historical social group for that capture. Do not replace it automatically using a present-day sett-to-group lookup.

---

### `analysis.diagnostic_results`

**One row per diagnostic result.**

A single capture can therefore have several rows in this view.

It brings the main diagnostic tests into one long-format table, including records from:

- culture;
- IFN-gamma ELISA;
- DPP;
- Stat-Pak;
- ELISA;
- Brock.

Use this for test histories and diagnostic analyses.

**Important:** do not join this directly to `capture_history` and then assume the result is still one row per capture. One capture can have several diagnostic rows.

---

### `analysis.infection_probabilities`

**One row per capture × infection-model variant.**

This contains the probabilistic infection histories generated by the infection model.

Use this when you want to select or compare infection-model variants, including the preferred `all_tests_inferred` results.

---

### `analysis.capture_infection_probabilities`

**One row per capture.**

This is a wide version of the infection probabilities, with the different model variants in separate columns.

Because it remains one row per capture, it can be joined to `analysis.capture_history` by `capture_id` without multiplying capture rows.

---

### `analysis.sett_social_group_observed`

Observed historical sett/social-group/year combinations.

Use this as an observed historical summary. It is **not** a rule saying a sett could only ever belong to one group in a particular year.

---

## 3. Cleaned tables already available in `research`

Most people should start with the `analysis` views above. The `research` schema is there when more detail is needed.

Useful core tables include:

- `research.individuals` — one row per badger;
- `research.captures` — one row per capture;
- `research.capture_sampling` — biological sampling associated with captures;
- `research.capture_assessments` — clinical/health assessments;
- `research.capture_collars` — collar information;
- `research.wounds` — wound records;
- `research.setts` — cleaned sett lookup;
- `research.social_groups` — cleaned social-group lookup.

Diagnostic tables include:

- `research.cultures`;
- `research.ifn_gamma_elisa`;
- `research.dpp_tests`;
- `research.stat_pak`;
- `research.elisa_tests`;
- `research.brock_tests`.

So in most cases the cleaning and restructuring work has already been done centrally. You should not need to go back to the raw Access tables.

## 4. Connecting from R

Database credentials are stored locally in `~/.Renviron` and are **not** stored in the repository.

The expected variables are:

```text
BADGER_DB_HOST=...
BADGER_DB_PORT=5432
BADGER_DB_NAME=postgres
BADGER_DB_USER=...
BADGER_DB_PASSWORD=...
```

Use the Supabase **Session Pooler** on port **5432**.

Never commit the real `.Renviron` file or paste the password into scripts, Markdown files, screenshots or logs.

The repository already contains:

```text
scripts/BadgerDatabase.R
```

so there is no need to write a new connection script.

Start an R session from the project root and run:

```r
source("scripts/BadgerDatabase.R")

con <- badger_db_connect()
```

When finished:

```r
dbDisconnect(con)
```

## 5. The easiest way to load data

The helper script already contains simple functions.

Load all capture-history rows:

```r
captures <- load_capture_history(con)
```

Load only live captures:

```r
captures <- load_capture_history(
  con,
  live_only = TRUE
)
```

Load a date range:

```r
captures <- load_capture_history(
  con,
  start_date = "2015-01-01",
  end_date   = "2020-12-31"
)
```

Load diagnostic results:

```r
diagnostics <- load_diagnostics(con)
```

Load only culture results:

```r
culture <- load_diagnostics(
  con,
  test_family = "Culture"
)
```

These helper functions return ordinary R data frames.

## 6. Querying the database without downloading everything

For larger jobs it is better to create a remote reference first:

```r
captures <- capture_history_db(con)
diagnostics <- diagnostic_results_db(con)
```

Then filter or summarise on the database before using `collect()`:

```r
library(dplyr)

dat <- captures %>%
  filter(primary_year >= 2015) %>%
  select(
    individual_id,
    capture_id,
    tattoo,
    capture_date,
    primary_year,
    sex,
    age_fc,
    normalized_sett_name,
    socg
  ) %>%
  collect()
```

Think of the workflow as:

```text
filter/select/summarise in PostgreSQL
              ↓
           collect()
              ↓
continue locally in R
```

## 7. Accessing the other ready-made analysis views

The current helper script has dedicated shortcuts for capture history and diagnostics.

Other views can be opened directly:

```r
library(dplyr)
library(dbplyr)

infection_probs <- tbl(
  con,
  in_schema("analysis", "infection_probabilities")
)

capture_infection_probs <- tbl(
  con,
  in_schema("analysis", "capture_infection_probabilities")
)

sett_group_history <- tbl(
  con,
  in_schema("analysis", "sett_social_group_observed")
)
```

You can then filter these remotely and call `collect()` when ready.

## 8. Important rules

- **Start with `analysis` whenever possible.**
- Treat `access_raw` as an archive, not an analysis dataset.
- Keep `capture_id` and `individual_id` in derived datasets wherever possible.
- Remember that `capture_history` is one row per capture but `diagnostic_results` is one row per diagnostic result.
- For spatial work, prefer cleaned sett identifiers such as `sett_id` and `normalized_sett_name`.
- Do not reinterpret historical social group from current sett mappings.
- Disease classes are not equivalent to a single diagnostic test.
- If a new cleaned variable is likely to be useful repeatedly, it is better to create it centrally than for several people to clean it independently.
- Disconnect from the database when finished.

## 10. Minimal quick start

For most collaborators this is enough:

```r
source("scripts/BadgerDatabase.R")

con <- badger_db_connect()

captures <- load_capture_history(
  con,
  start_date = "2015-01-01",
  live_only = TRUE
)

dbDisconnect(con)

glimpse(captures)
```

If you need diagnostic data as well:

```r
source("scripts/BadgerDatabase.R")

con <- badger_db_connect()

captures <- load_capture_history(con)
diagnostics <- load_diagnostics(con)

dbDisconnect(con)
```
